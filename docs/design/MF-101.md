# MF-101 Organizers create their own events

Status: implemented on branch `mf-101-create-events`; assumptions A1–A6 still wait on the PO
Author: Aleksandar Petrushev
Date: 2026-10-27

## Problem

Organization admins cannot create events in My Forum. The API has `update` and `destroy` for events but no `create`, so events only appear through seeds or the platform team.

## Requirements

From the ticket and the PO's refinement notes on 2026-10-27:

- Any admin of an organization can create an event for that organization, and only that organization. An admin of several organizations picks which one the event belongs to. Plain members cannot create events.
- An event is created as a draft or as published.
  - A draft is visible only to the organizing organization's admins: not in discovery, no registrations, no notifications. Nobody else may see a draft, including through a direct link.
  - A published event shows in discovery for the right people and is open for registration.
  - Admins can publish a draft later. A published event never goes back to draft.
- An organization-restricted event takes a list of allowed organizations.
- A newly published event appears in discovery within one minute for the people the existing visibility rules allow.
- No notifications in this ticket. Notifying topic followers about new events comes later and must stay easy to add.

## Assumptions waiting on the PO

The design below is built on these. If the PO answers differently, only the sections named in the last column change.

| # | Assumption | Review | Changes if wrong |
|---|---|---|---|
| A1 | A newly published event reaches the Go read model in this ticket, so it can be recommended. | R2 | Go service |
| A2 | Admins set topics when they create an event. | R7 | Request, form |
| A3 | An organization-restricted event needs at least one allowed organization, on create and on update. | R8 | `Events::AllowedOrganizations` |
| A4 | Any admin may see the names of all organizations when picking allowed organizations. | R10 | Organizations endpoint |
| A5 | The admin enters times in their browser's time zone; the client sends ISO 8601 with an offset. | R11 | Form |
| A6 | A published event can never go back to draft, whether or not anyone has registered. | R3 | Status rules |

## Design

### Backend

**Endpoint.** `POST /api/events`, handled by a new `create` action on `Api::EventsController`. The route becomes `resources :events, only: [:index, :show, :create, :update, :destroy]`.

**Request.**

| Field | Required | Notes |
|---|---|---|
| `organization_id` | yes | Must be an organization the user administers |
| `title`, `description`, `location` | yes | Existing model validations |
| `starts_at`, `ends_at` | yes | ISO 8601 with offset; `ends_at` must be after `starts_at` |
| `kind` | yes | `online` or `in_person` |
| `capacity` | yes | Integer greater than 0 |
| `status` | no | `draft` or `published`; defaults to `draft`. Any other value is a 422 (R6) |
| `visibility` | no | `public` or `organization_restricted`; defaults to `public` |
| `allowed_organization_ids` | for restricted | Ignored for public events. For restricted events, every id must exist and the list must not be empty (R8, A3) |
| `topic_ids` | no | Every id must exist (A2) |

Create uses its own permitted parameters. It does not share `event_params` with `update`, because `update` permits fields such as `cancelled` status that create must refuse.

**Authorization.** Add `EventPolicy#create?`. It allows the request only when the current user is an admin of the organization the event belongs to, reusing the private `admin_of_organizer?`. The controller builds the unsaved event with the requested `organization_id` and calls `authorize` before anything is written.

**Draft visibility (R1).** Drafts must not leak through a direct link or through registration. Today `EventPolicy#show?` and `EventPolicy::Scope` ignore `status`, and `Events::Register` does not check it.

- `EventPolicy#show?` and `EventPolicy::Scope#resolve` allow a non-published event only for admins of the organizing organization. Published events keep today's rules.
- `Events::Register` refuses any event that is not published. A registration attempt for a draft returns 404, the same as an event the caller cannot see.
- `index` keeps its `.published` filter, so drafts never appear in discovery, even for the organizer's admins.

**Service.** A new `Events::Create` service in `backend/app/services/events/create.rb`, alongside `Events::Update` and `Events::Register`. In one transaction it:

1. Creates the `Event` record.
2. Creates `event_allowed_organizations` rows for a restricted event, and `event_topics` rows.
3. If the event is published, records `EventPublished` (see below).

After the transaction commits, it writes the detail cache entry with `Events::Cache.write_detail` (R5).

**Publishing is one transition (R3).** `EventPublished` marks the moment an event becomes published, whether that happens on create or later through `Events::Update`. Both services call one shared step, `Events::Publication.record!(event)`, when the status moves to `published`. Its idempotency key is `event_published:<event id>`, so the unique index on `outbox_events.idempotency_key` keeps it to one row per event, however many times it is called (R4). `Events::Update` keeps writing `EventUpdated` for every change as it does today.

**Status rules (R3, R6, A6).**

- Create accepts `draft` or `published` and defaults to `draft`.
- `Event` validates that a published event cannot move back to `draft`. This covers `Events::Update` as well as create.

**Response.** A successful create returns `201 Created` with `Event#as_detail_json` plus `allowed_organization_ids`, which the detail JSON does not carry today:

```json
{
  "id": 101,
  "title": "Financing the energy transition",
  "description": "A working session for partners.",
  "starts_at": "2026-11-20T09:00:00Z",
  "ends_at": "2026-11-20T10:30:00Z",
  "location": "Geneva",
  "kind": "in_person",
  "capacity": 80,
  "reserved_spots": 0,
  "status": "published",
  "visibility": "organization_restricted",
  "organization": { "id": 3, "name": "Example Org" },
  "topics": [{ "id": 7, "name": "Climate", "slug": "climate" }],
  "speakers": [],
  "allowed_organization_ids": [4, 5]
}
```

**Errors (R8, R9).** Every validation failure uses the existing `validation_failed` shape, so clients handle one format. `details` keeps today's human-readable messages per field. A new sibling key, `reasons`, carries the stable error type per field (`errors.details`), so clients can match on a reason without parsing messages. `reasons` is additive, so existing clients are unaffected.

| Case | Status | Body |
|---|---|---|
| No or invalid token | `401` | `{"error": {"code": "unauthenticated", ...}}` |
| User is not an admin of the event's organization | `403` | `{"error": {"code": "forbidden", ...}}` |
| `ends_at` is not after `starts_at` | `422` | `{"error": {"code": "validation_failed", ..., "details": {"ends_at": ["must be after starts_at"]}, "reasons": {"ends_at": [{"error": "ends_before_start"}]}}}` |
| Unknown allowed organization or topic id | `422` | `validation_failed`, with the field named in `details` |
| Restricted event with no allowed organizations | `422` | `validation_failed`, `details.allowed_organization_ids` |
| `status` other than `draft` or `published` | `422` | `validation_failed`, `details.status` |
| Any other validation failure | `422` | `validation_failed` with `details`, unchanged |

The model adds the end-time error as `errors.add(:ends_at, :ends_before_start)`, so `reasons` carries it. The existing rule rejects an end equal to the start, so the check is "ends after start", not "ends before start". Unknown ids are validated before insert, so they never reach the foreign key and never return 500.

**Caching (R5).**

- `Event` already has `after_commit :invalidate_event_caches` on create. It deletes the detail key and bumps the list epoch, so the upcoming list cache is invalidated on create without extra work.
- The detail cache entry is written after the transaction commits. Written inside the transaction, the `after_commit` would delete it; written before commit, it could cache an event that rolls back.

### Personalization (A1, R2)

`Outbox::Dispatcher` already sends every outbox row to the Go service. Go's ingest switch in `personalization/internal/store/postgres.go` (and `memory.go`) ignores unknown types, so `EventPublished` would be dropped. Add `EventPublished` to the existing event upsert case beside `EventUpdated`, using the same `event` snapshot payload. Ranking needs no change, because Go already ranks only events with `status = 'published'`.

### Organizations endpoints

- `GET /api/me/organizations` in a new `Api::Me::OrganizationsController`, routed in the existing `namespace :me` block. It returns `id` and `name` for each organization where the current user's membership has `role: "admin"`. The create page uses it for the organization select; the events page uses it to decide whether to show the create button.
- `GET /api/organizations` returns `id` and `name` of every organization, for the allowed-organizations picker (R10, A4). It is limited to users who are an admin of at least one organization.

### Frontend

- **Shared admin state (R11).** A small service loads `GET /api/me/organizations` once per session and exposes it to the events page and the create page. Hiding the button is a convenience; the API policy is the control.
- **Create button.** A "Create event" button on the events page (`discovery.component.ts`), shown only when the user is an admin of at least one organization.
- **Route.** The form has its own route, guarded by `authGuard`. A signed-in user with no admin organizations who opens it sees a message that only organization admins can create events.
- **Form.**
  - An organization select filled from the shared admin state.
  - Topic selection from `GET /api/topics` (A2).
  - Start and end times entered in the browser's time zone and sent as ISO 8601 with an offset (A5).
  - A visibility choice: public or organization restricted. When restricted is chosen, a list to add allowed organizations, filled from `GET /api/organizations`.
  - Status: save as draft or publish.
- **Submit.**
  - On submit the button is disabled and its label changes to "Creating...". The form sends the request to `POST /api/events` through a new `ForumApi` method.
  - On `201`, navigate to `/events/:id`.
  - On `422`, show each field's error from `details` and re-enable the button.

## Out of scope

- Notifying topic followers about new events (a later ticket, which will listen for `EventPublished`).
- An `Idempotency-Key` header for client retries. A duplicate event from a retried request can be deleted by the admin (R4).
- Platform staff creating events for other organizations.
