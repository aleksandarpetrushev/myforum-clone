# MF-102 Cancelling an event cancels its registrations and tells registrants

Status: implemented on branch `mf-102-cancel-events`
Author: Aleksandar Petrushev
Date: 2026-10-28

## Problem

An admin can set an event's status to `cancelled` today through `PATCH /api/events/:id`, but nothing else happens. Registrations stay confirmed, nobody is told, and registrants who open the event get "not found".

## Requirements

From the ticket and the PO's answers on 2026-10-28:

- When an admin cancels an event, every confirmed registration ends as cancelled **by the organizer**, and each registrant is notified once, even if a job retries.
- Nothing counts a registrant of a cancelled event as attending. Reports must not show a cancelled event's registrations as if it happened.
- A cancelled event stays cancelled: it cannot be published again or turned back into a draft.
- Cancelled events never appear in discovery or recommendations.
- Registrants, and anyone else allowed by the normal visibility rules, can still open a cancelled event's page. It shows a clear **Cancelled** label and the cancellation date, never "not found".
- The organizer's admins keep seeing their cancelled events.
- My registrations keeps the event, marked as cancelled by the organizer.

## How the code behaves today

| Area | Today | Consequence for MF-102 |
|---|---|---|
| Cancel path | `PATCH /api/events/:id` with `status: "cancelled"` goes through `Events::Update`, which writes one `EventUpdated` row and nothing else | No registration changes, no notifications |
| Status rules | `Event#published_stays_published` blocks a return to draft, but `cancelled` → `published` is still allowed | Breaks "cancelled stays cancelled" |
| Visibility | `EventPolicy#show?` and `Scope` (MF-101) show non-published events only to the organizer's admins | Registrants get 404 on a cancelled event |
| My registrations | `Api::Me::RegistrationsController` hides the event's title, time and location when `policy_scope(Event)` excludes it | Registrants see a cancelled registration with no event name |
| Per-user cancel | `Registrations::Cancel` locks the event, cancels one registration, decrements `reserved_spots`, writes `RegistrationCancelled` keyed by `lifecycle_version` | Reusable, but refuses with `EventStarted` once the event has started |
| Registration states | `confirmed`, `cancelled`, `failed`; nothing records who cancelled | "Cancelled by the organizer" cannot be told apart from a self-cancel |
| Notifications | `SendNotificationJob` turns `RegistrationCancelled` into kind `registration_cancelled`, which the user can mute. `NotificationPreference.allows?` returns true for any kind it does not know | A new notification kind cannot be muted unless a preference column is added |
| Discovery | `index` filters `.published` | Already excludes cancelled events |
| Recommendations | Go upserts the event from the `EventUpdated` snapshot; Postgres candidates require `status = 'published'` | Already drops a cancelled event once `EventUpdated` is ingested |
| Registration | `Events::Register` refuses non-published events (MF-101) | Already refuses cancelled events |

## Decisions

Decided on 2026-10-28.

| # | Decision | Choice |
|---|---|---|
| D1 | How an admin cancels | Dedicated `POST /api/events/:id/cancel` calling an `Events::Cancel` service. `PATCH /api/events/:id` accepts any status and the `Event` state machine validates it, but never `cancelled`: only the machine's `cancel` event can cancel, and only `Events::Cancel` fires it (code review, 2026-10-28) |
| D2 | How the cascade runs | In a job, after the request |
| D3 | Recording "cancelled by the organizer" | A new `EventCancelled` outbox event (see G1: this records the event, not each registration) |
| D4 | Notification kind | New kind `event_cancelled`, with a new preference column. Defaults to on (PO) |
| D5 | Seat count | Lowered as each registration is cancelled (changed by G3); reports ignore cancelled events anyway |
| D6 | Who can see a cancelled event | Only drafts are hidden from participants. Cancelled events follow the same public and restricted rules as published ones |
| D7 | Status rules | A `state_machine :status` on `Event`: `publish` (draft to published) and `cancel` (published to cancelled, which sets `cancelled_at`). A validation checks plain status writes against the same machine |
| D8 | Frontend | The admin sees a Cancel button on the event page, with a confirmation dialog. Users receive the new notification kind and can switch it in their preferences |

PO answers on 2026-10-28:

- Q1: one notification per registrant, of kind `event_cancelled`, never `registration_cancelled` as well. Its preference defaults to on.
- Q2: late cancellations (within 24 hours of the start) go to the backlog as their own ticket.
- Q3: organizers cannot cancel an event once its start time has passed. Rare mid-event cases are handled by the platform team.
- Q4: no cancellation reason for now.

## Gaps in the decisions

Resolved on 2026-10-28:

| # | Gap | Resolution |
|---|---|---|
| G1 | How a registration records who cancelled it | A `cancelled_by` column on `registrations`: `participant` or `organizer` |
| G2 | D1 removed the only way to publish a draft | Superseded by the revised D1: `PATCH` accepts any status and the state machine allows only draft to published there |
| G3 | The job cannot reuse `Registrations::Cancel` as it is | The seat count is lowered after all (D5 changed), which removes one conflict. P1 covers the rest |
| Go | A cancelled event must leave recommendations | Go's ingest learns `EventCancelled` and upserts the snapshot, as it does for `EventUpdated` |
| Repeat | Cancelling an event that is already cancelled | `200` with the event as it is, and no further effect: no new outbox row, no job, `cancelled_at` unchanged |
| Date | Where the cancellation date comes from | A `cancelled_at` column on `events`, set once by `Events::Cancel` |
| Draft | Cancelling a draft | `422`; a draft has no registrants, so the admin deletes it instead |

**P1. Proposal: the job cancels each registration with its own step, not by calling `Registrations::Cancel`.** Two conflicts remain even with the seat count lowered:

- `Registrations::Cancel` writes a `RegistrationCancelled` row, and `SendNotificationJob` turns that into a `registration_cancelled` notification. The PO wants exactly one `event_cancelled` notification per registrant (Q1), not two.
- `Registrations::Cancel` raises `EventStarted`. An event cancelled just before its start time can have its job run after the start, and that job must still finish.

So the job, for each confirmed registration: locks it, moves it to `cancelled` with `cancelled_by: "organizer"`, bumps `lifecycle_version`, lowers `reserved_spots` by one, and creates one `event_cancelled` notification keyed `notification:event_cancelled:<registration id>`. It skips the notification when the user's `event_cancelled_enabled` preference is off. It skips registrations that are already cancelled. Rerunning the job therefore changes nothing and sends nothing twice. The step shares its locking and state change with `Registrations::Cancel` through one small method, rather than copying it.

**Background to the gaps.**

**G1. D3 does not say how a registration records who cancelled it.** `EventCancelled` records that the event was cancelled, but each registration still ends in the same `cancelled` state as a self-cancel. That matters for test 3: someone who cancelled their own registration earlier must keep that, and must not get the organizer's notification. My registrations also needs to tell the two apart. Options: a `cancelled_by` column on `registrations`, or derive it at read time from the registration's cancellation time compared with the event's.

**G2. D1 removes the only way to publish a draft.** MF-101 publishes a draft with `PATCH /api/events/:id` and `status: "published"`, and `Events::Update` records `EventPublished` on that transition. If `PATCH` no longer accepts `status`, admins can create drafts but never publish them. Options: `PATCH` accepts only the draft-to-published change, or a dedicated `POST /api/events/:id/publish` that matches the cancel endpoint.

**G3. D2 and D5 rule out reusing `Registrations::Cancel`.** That service decrements `reserved_spots` and raises `EventStarted`. The job needs its own per-registration step that cancels without touching the seat count. It also has to be safe to run twice, and it has to finish even if the event's start time passes before the job runs.

**Also needed, from the MF-101 lesson:** Go's ingest switch must learn `EventCancelled`, or the event stays a recommendation candidate. The alternative is for `Events::Cancel` to also write `EventUpdated`, which Go already handles.

## Failure handling

The cascade job can run any number of times. Each registration is cancelled in its own transaction, locking only that registration (and then the user, for the preference check), and is skipped once it is no longer confirmed. The notification is written in the same transaction. The event row is not locked per registration: after the loop, one statement sets `reserved_spots` to the number of registrations still confirmed, and the cache is invalidated once (code review finding 4). A failure on one registration is logged as `event.cancel.registration_failed` and counted; the rest still finish, and the job then raises so Sidekiq retries. If retries run out, `Metrics.cancelled_events_with_confirmed_registrations` stays above 0, and `bin/rails events:resume_cancellations` re-enqueues the cascade.

## Options considered

The options below were weighed for each decision.

**D1. How an admin cancels.**

- A. Keep `PATCH /api/events/:id` with `status: "cancelled"`, and make `Events::Update` cascade when the status changes to cancelled.
- B. A dedicated `POST /api/events/:id/cancel` with an `Events::Cancel` service, and `PATCH` refuses `status: "cancelled"`. This leaves room for a reason or a confirmation step.

**D2. How the cascade runs.**

- A. Synchronously: one transaction locks the event, cancels every confirmed registration and writes one `RegistrationCancelled` row each. This reuses `SendNotificationJob`, analytics and the Go handler as they are. At the 3,000-participant scale of MF-302, that is one transaction with 3,000 outbox rows.
- B. Asynchronously: the request cancels the event and writes one `EventCancelled` row. A job then cancels registrations and notifies in batches. The request stays fast, but there is a window where the event is cancelled and registrations still read confirmed.

**D3. Recording "cancelled by the organizer".**

- A. A new column on `registrations`, for example `cancelled_by` (`participant` or `organizer`).
- B. A new state such as `cancelled_by_organizer` in the `Registration` state machine.
- C. Derive it: a cancelled registration on a cancelled event. This is wrong for someone who cancelled their own registration before the organizer cancelled the event.

**D4. Notification kind (needs the PO, see Q1).**

- A. Reuse kind `registration_cancelled`; users who muted it hear nothing.
- B. A new kind, `event_cancelled`, with its own copy. It cannot be muted unless you also add a preference column.

**D5. Seat count.**

- A. Decrement `reserved_spots` to 0, so every count of the event reads zero.
- B. Leave `reserved_spots` as it was, and make reports exclude cancelled events.

Tell the PO which, as agreed.

**D6. Who can see a cancelled event.**

Today only the organizer's admins can see a non-published event. To meet the requirement, `EventPolicy#show?` and `Scope` need to let a cancelled event through under the same public and restricted rules as a published one, while drafts stay admin-only. Discovery keeps its `.published` filter. Decide whether `Scope` changes, or only `show?` and the My registrations lookup.

**D7. Status rules.**

Extend the model rule so a cancelled event can never change status again. Decide whether that lives in `Event` validations (it covers every path) or in the cancel service.

**D8. Frontend.**

- Where the admin's cancel action lives (the event page is the obvious place), and how it asks for confirmation. `registrations.component` has a confirm pattern to reuse.
- The **Cancelled** label and the cancellation date on the event page.
- "Cancelled by the organizer" on My registrations.
