# MF-201 "Recommended for you" on the discovery page

Status: decided, ready for planning
Author: Aleksandar Petrushev
Date: 2026-11-09

## Problem

The Go service ranks events for each user, but no screen shows the result. Nothing in Rails or Angular calls `GET /recommendations` today.

## Requirements

From the ticket and the PO on 2026-11-09:

- Discovery shows up to five recommended events for the signed-in user.
- A recommended event is never one the user cannot see.
- If personalization is slow or down, discovery still loads in its normal time.
- Following a new topic changes the list within one minute.
- Events the user is already registered for are not recommended.
- Full events are not recommended until waitlists exist (PO, 2026-11-09, after the end-to-end run).
- An empty list shows "No recommendations yet". A failure shows "Recommendations not available currently, try again later".

## How the code behaves today

| Area | Today |
|---|---|
| Go endpoint | `GET /recommendations?user_id=<id>` returns up to 10 events (`event_id`, `title`, `location`, `starts_at`, `score`). No authentication: any caller can ask for any user's list |
| Go eligibility | `Candidates` repeats `EventPolicy::Scope` in its own SQL and checks the projection's `status`, not the live event's |
| Go and registrations | `RegistrationCreated` and `RegistrationCancelled` only update the event's seat count in the read model. Go does not know who is registered for what |
| Go server | No read or write timeouts |
| Topic follows | `TopicFollowed` reaches Go through the outbox within 1–5 s |
| Rails to Go | `Personalization::DeliverEvent` uses `Net::HTTP` with 2 s timeouts |
| Discovery page | `discovery.component.ts` loads topics and events with signals; no recommendations |

## Decisions

| # | Decision | Choice | Reason |
|---|---|---|---|
| D1 | Who calls Go | Rails, through a new `GET /api/me/recommendations`. Angular never calls Go | Go has no authentication; Rails already authenticates the user. Go stays internal |
| D2 | Who decides visibility | Rails filters every id Go returns through `policy_scope(Event).published.upcoming` | Rails owns authorization. `policy_scope` alone also returns cancelled events, and Go's projection can lag a cancellation by seconds |
| D3 | Registered events | Rails drops events the user has a `confirmed` registration for | Rails has the registrations; Go does not, and teaching it needs a per-user table in its read model and new payload fields (MF-203). A cancelled registration can be recommended again |
| D4 | How many to ask Go for | Go gains an optional `limit` parameter (default 10, maximum 50). Rails asks for 20 and keeps the first 5 that pass D2 and D3, in Go's order | With 10, a user registered for several top events would see fewer than five |
| D5 | Event details | Taken from Rails' event rows (`Event#as_list_json`), not from Go's projection | A recommended card shows the same title, time and location as the rest of discovery |
| D6 | Timeouts | 250 ms to connect, 1 s to read | A Puma thread waits for the whole call. At 5 s, a hung Go service would hold every thread within seconds and slow discovery itself. Go's ranking is one SQL query, normally tens of milliseconds |
| D7 | Loading | Angular requests recommendations separately from the event list, after the page renders | A slow or failing Go service can never delay discovery |
| D8 | Cache | Go's ranked id list per user, 30 s fresh. Visibility (D2) and registrations (D3) are filtered on every request, cached or not | Outbox lag (1–5 s) plus 30 s stays under the one-minute rule. Filtering after the cache means losing access or registering takes effect at once, as in ADR 0005 |
| D9 | No cache delete on follow | The cache is not deleted when a user follows a topic | Go updates asynchronously; deleting at once could cache the old list again before Go catches up |
| D10 | Go fails | Serve the last cached list even if it is past 30 s, and treat it as fresh for another 30 s so Go is not asked again on every request. With no cached list, return `503 recommendations_unavailable` | Most users never see the error, and during an outage each user waits for a timeout at most once per 30 s |
| D11 | Empty and error states | 200 with an empty list shows "No recommendations yet". Any error shows "Recommendations not available currently, try again later" | An empty list is not a failure |
| D12 | Full events | Rails drops events with no seats left (`reserved_spots >= capacity`) | Found in the end-to-end run: Go's ranking rewards fullness, so full events ranked first and registering for them failed. PO, 2026-11-09: don't recommend what can't be booked. Remove when MF-202 adds waitlists |

## Design

### Go

`GET /recommendations` reads an optional `limit`: default 10, values above 50 are capped at 50, values below 1 return 422. Nothing else changes.

### Rails

`Personalization::Recommendations.ids_for(user)`:

```ruby
CACHE_TTL = 30.seconds
KEEP_STALE_FOR = 1.day

def self.ids_for(user)
  key = "recommendations/v1/u#{user.id}"
  cached = read_cache(key) # { "ids" => [...], "fetched_at" => epoch seconds }, or nil
  return cached["ids"] if cached && Time.current.to_i - cached["fetched_at"] < CACHE_TTL

  ids = fetch_from_go(user.id, limit: 20) # Net::HTTP, open_timeout 0.25, read_timeout 1
  write_cache(key, { "ids" => ids, "fetched_at" => Time.current.to_i }, expires_in: KEEP_STALE_FOR)
  ids
rescue Personalization::Unavailable
  raise unless cached

  Rails.logger.warn({ event: "recommendations.stale", user_id: user.id }.to_json)
  cached["ids"]
end
```

- One cache entry per user holds the ids and when they were fetched. Under 30 s old it is fresh; older, it is used only when Go fails.
- `Personalization::Unavailable` covers timeouts, connection errors, non-2xx responses and unparseable bodies.
- Cache read and write errors are rescued and logged, so Redis being down means calling Go every time, not failing.

Two layers, so the rule for what a user may be recommended is separate from how Rails talks to Go:

| Class | Owns |
|---|---|
| `Personalization::Http` | The one way Rails reaches Go, shared with `DeliverEvent`. Retries off, so a timeout means exactly that long |
| `Personalization::Client` | The recommendations call and its timeouts. Any failure becomes `Personalization::Unavailable` |
| `Personalization::Recommendations` | The cache and stale-on-failure. Returns ranked ids |
| `Recommendations::ForUser` | Which of those ids this user gets: visibility (D2), registrations (D3), the top five (D4) |
| `Api::Me::RecommendationsController` | Calls `ForUser`, renders, maps `Unavailable` to 503 |

`Recommendations::ForUser`:

```ruby
module Recommendations
  class ForUser
    LIMIT = 5

    def initialize(user:)
      @user = user
    end

    # Go ranks; Rails decides what this user may be shown. Raises Personalization::Unavailable
    # when Go fails and there is no cached list to fall back on.
    def call
      ids = Personalization::Recommendations.ids_for(@user)
      return [] if ids.empty?

      registered = @user.registrations.where(status: "confirmed", event_id: ids).pluck(:event_id)
      events = Pundit.policy_scope!(@user, Event).published.upcoming.where(id: ids - registered).index_by(&:id)
      ids.filter_map { |id| events[id] }.first(LIMIT)
    end
  end
end
```

`Api::Me::RecommendationsController#index`:

```ruby
events = Recommendations::ForUser.new(user: current_user).call
render json: { "data" => events.map(&:as_list_json) }
rescue Personalization::Unavailable
  render_error(code: "recommendations_unavailable", message: "Recommendations are not available right now.", status: :service_unavailable)
```

`Pundit.policy_scope!` resolves the same `EventPolicy::Scope` the controllers use. Nothing in `BaseController` verifies that a controller called `policy_scope` itself, so calling it from the service changes no check.

The response is `{ "data": [...] }`, each row the same shape as a discovery list row.

Metrics: `recommendations_success_total`, `recommendations_stale_total`, `recommendations_unavailable_total`.

### Frontend

- `ForumApi#recommendations()` calls `GET /api/me/recommendations`.
- `discovery.component.ts` gains `recommendations` and `recommendationsState` (`loading`, `ready`, `failed`) signals. It requests recommendations on its own subscription, in parallel with the event list, and neither waits on the other.
- A "Recommended for you" section above the results. While loading: a short placeholder. Empty: "No recommendations yet". Failed: "Recommendations not available currently, try again later". Each card links to the event.

## Out of scope

- Authentication on the Go service. It stays reachable only from Rails' network; this is noted as a risk, not fixed here.
- Removing Go's copy of the visibility rule. D2 makes it redundant for safety; MF-303 decides its future.
- A circuit breaker. The 1 s read timeout bounds the cost of a hung Go; revisit if `recommendations_unavailable_total` shows sustained failures.
