# MF-106 Saving an event twice never fails and never doubles

Status: decided, ready for planning
Author: Aleksandar Petrushev
Date: 2026-11-09

## Problem

The ticket reports that two saves to the same event within one second return 422. Reproducing it showed a wider bug: a save that changes nothing returns 422 at any time, not only within the same second.

The `EventUpdated` outbox key is `event_updated:<id>:<updated_at in whole seconds>`. A save that changes nothing leaves `updated_at` as it was, so it rebuilds the previous save's key and fails the uniqueness validation.

Reproduced on 2026-11-09, each save in its own transaction:

| Save | Result |
|---|---|
| 1. New title A | ok, 1 outbox row |
| 2. Same title A, same second | 422 |
| 3. Different title B, same second | 422, title stays A |
| 4. Title A again, 2 s later | 422 |
| 5. Same again, 2 s after that | 422 |

## Requirements

From the ticket:

- The same changes saved twice: both saves succeed, the change happens once, and there are no duplicate outbox rows or notifications.
- Two different saves in quick succession: both succeed and both changes are kept. The second is never rejected or lost.
- "Success" never means the old version was quietly kept.

## How the code behaves today

| Area | Today |
|---|---|
| Key | `event_updated:#{id}:#{updated_at.to_i}`, built after `update!` |
| Duplicate key | `OutboxEvent` validates `idempotency_key` uniqueness, so a repeat raises `RecordInvalid` (422) and the transaction rolls back. `OutboxEvent.record!` also catches `RecordNotUnique` and returns the existing row, which would drop the second change's event silently if two saves raced past the validation |
| Locking | None. `Events::Update` validates allowed organizations and applies attributes to the event the controller loaded, without locking the row |
| No-op saves | Still write `EventUpdated`, invalidate the cache and enqueue `RebuildEventCacheJob` |
| Consumers | `EventUpdated` feeds analytics and the Go read model. It sends no notifications |
| Go | `applyTx` upserts every event snapshot unconditionally. `RegistrationCreated`, `RegistrationCancelled`, `EventPublished`, `EventCancelled` and `EventUpdated` all carry a snapshot |
| Delivery order | One polling chain delivers in id order. If `ProcessOutboxJob` is enqueued twice, two chains run side by side and rows for the same event can arrive out of order |
| Intent | `update_spec.rb` says "a second update in the same second is refused, not dropped": refusing was chosen over dropping. The ticket now asks for neither |

## Decisions

| # | Decision | Choice | Reason |
|---|---|---|---|
| D1 | What makes a change unique | A per-event `revision` counter, incremented by every change to the event row: an `Events::Update` that changes something, a cancellation, a registration, a cancelled registration, and the cancellation cascade's seat recount. Key `event_updated:<id>:<revision>` | Unique per change by construction. A content hash would reuse a key when an event is edited from A to B and back to A, dropping that change; a random id per save would duplicate rows when the same save is sent twice |
| D2 | A save that changes nothing | Return 200 with the current event and write nothing: no revision bump, no outbox row, no cache invalidation, no cache rebuild job. The unchanged row is not validated again | "The change happens once". A stored event is always valid, and nothing about it changed (decided in review, 2026-11-09) |
| D3 | Concurrent saves | Lock the event row (`SELECT … FOR UPDATE`) at the start of the transaction, then apply the attributes. Saves to one event run one after the other; both succeed; on the same field the later one wins | "Never rejected" rules out optimistic locking (`lock_version` would reject the second save) |
| D4 | Validation | Allowed-organization validation moves inside the lock, after the reload | Validating the copy the controller loaded could judge a list another save has just changed |
| D5 | Writing the outbox row | `OutboxEvent.create!`, not `record!` | With the lock and the revision a collision cannot happen, so if one ever does it must fail loudly, never return the old row |
| D6 | Revision in the payload | `Event#snapshot` gains `revision`, so every event type that carries a snapshot sends it | Go can tell an older snapshot from a newer one |
| D7 | Go honours the revision | `personalization.events` gains `revision`; the upsert applies a snapshot only when its revision is greater than or equal to the stored one | Out-of-order delivery (two polling chains, a retried row) can no longer overwrite a newer state with an older one: not a title, not a seat count, and not a cancellation. Because every change takes a new revision, an equal revision is the same state sent twice |
| D8 | Snapshots without a revision | Written before the deploy. Go applies them as it did before (last to arrive wins) and never lowers the stored revision | Treating them as revision 0 would drop them once the event has a revision, including registrations written by old code still running during a rolling deploy. Applying them keeps pre-MF-106 behaviour for the rows that were already in flight |

## Design

### Database

Migration: `add_column :events, :revision, :integer, null: false, default: 0`. Existing events start at 0. The first update after deploy writes `event_updated:<id>:1`. Old keys used 10-digit Unix seconds, so new and old keys cannot collide.

### `Events::Update#call`

```ruby
def call
  changed = false
  ApplicationRecord.transaction do
    @event.lock!                     # D3: reloads the row FOR UPDATE
    allowed_ids = extract_allowed_ids
    validate_allowed_organizations!(allowed_ids)   # D4
    was_published = @event.status == "published"

    @event.assign_attributes(@attributes)
    orgs_changed = !allowed_ids.nil? && allowed_ids.sort != @event.allowed_organization_ids.sort
    changed = @event.changed? || orgs_changed
    next unless changed               # D2

    @event.revision += 1
    @event.save!
    Events::AllowedOrganizations.replace(@event, allowed_ids) if orgs_changed
    OutboxEvent.create!(              # D5
      event_type: "EventUpdated", aggregate_type: "Event", aggregate_id: @event.id,
      idempotency_key: "event_updated:#{@event.id}:#{@event.revision}",
      payload: { "event" => @event.reload.snapshot }
    )
    Events::Publication.record!(@event) if !was_published && @event.status == "published"
  end
  return @event unless changed

  Events::Cache.invalidate(@event.id)
  RebuildEventCacheJob.perform_later(@event.id)
  @event
end
```

- `@event.touch` for an allowed-organizations-only change goes away: `revision += 1` and `save!` change `updated_at`.
- `Event#snapshot` adds `"revision" => revision`.
- The `Event` state machine still decides status changes; a refused transition still raises before anything is written.

### Go

- `personalization.events`: `ALTER TABLE … ADD COLUMN IF NOT EXISTS revision integer NOT NULL DEFAULT 0`, in the same startup schema setup as the table.
- The snapshot upsert adds `revision` and `WHERE personalization.events.revision <= EXCLUDED.revision` to `ON CONFLICT … DO UPDATE`. A snapshot without `revision` (an old pending row) reads as 0.
- The memory store applies the same rule.

| 9 | `PATCH /api/events/:id` twice with the same body | 200 both times | Request |

| 12 | Go: a late edit after a cancellation | The event stays cancelled | Go test |
| 13 | Go: seat counts out of order | The newest is kept | Go test |
| 14 | Go: snapshot without `revision` | Applied; the stored revision is kept; a later older revision is still ignored | Go test, memory and Postgres |

| 16 | Rails: cancellation cascade recount | Revision bumps | Job |

`update_spec.rb`'s comment and its `travel 1.second` go away: the second update in the same second now succeeds.

## Out of scope

- Telling an admin that someone else saved in between ("last write wins" is accepted for now).
- Stopping `ProcessOutboxJob` from running as two chains. D7 makes it harmless for event snapshots; the job itself is the outbox ticket's problem.
