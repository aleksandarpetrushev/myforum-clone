# MF-103 My registrations in Upcoming and Past

Status: decided, ready for planning
Author: Aleksandar Petrushev
Date: 2026-10-29

## Problem

A participant reported that My registrations "mixes last month's events with next week's". Triage found a missing feature, not a bug: `GET /api/me/registrations` returns every registration ordered by `registrations.created_at` descending, which is when the person registered, not when the event happens. Someone looking for tomorrow's session has to scroll past old ones.

## Requirements

From the PO on 2026-10-29:

- Show every registration, in two sections: **Upcoming** first, then **Past**.
- Upcoming is sorted by event start, soonest first. Past is sorted by event start, most recent first. No user-selectable sort.
- An event stays in Upcoming until it **ends**. An event in progress is marked "Happening now".
- Cancelled registrations (by the participant or the organizer) go under Past, marked as cancelled. Failed registrations go under Past, labelled "Registration failed". In Past they come after the events that took place.
- No Cancel button on an event that is happening now: the server refuses to cancel once an event has started.
- No pagination: one participant's history (around 100 to 150 registrations over several years) is not expected to be a problem. Revisit if it is.

## How the code behaves today

| Area | Today |
|---|---|
| Endpoint | `Api::Me::RegistrationsController#index` loads `current_user.registrations.includes(:event).order(created_at: :desc)` and returns `{ "data": [...] }` |
| Hidden events | When the caller can no longer see an event (`policy_scope(Event)` excludes it), the row is sent without its `event` summary: no title, time or location |
| Event summary | `Registration#event_summary` sends `id`, `title`, `starts_at`, `location`, `status`; no `ends_at` |
| Frontend | `registrations.component` renders `data` in the order received; the Cancel button shows for confirmed rows whose event is not cancelled |
| Callers | `spec/requests/api_spec.rb`, `spec/requests/events_cancel_spec.rb`, `registrations.component.spec.ts` and `ForumApi#registrations` read `data` |

## Decisions

| # | Decision | Choice | Reason |
|---|---|---|---|
| D1 | Where the split and sort happen | In the API | Rows for hidden events carry no dates, so only the server can place them. The client could not sort or split them |
| D2 | Response shape | `{ "upcoming": [...], "past": [...] }`, replacing `{ "data": [...] }` | Clearer than a per-row section field. Angular is the only client, so the contract change ships with its consumer in the same change |
| D3 | What is Upcoming | A `confirmed` registration whose event's `ends_at` is after now (server clock). Everything else is Past: ended, `cancelled` or `failed` | PO rules |
| D4 | Ordering | Upcoming by `events.starts_at ASC, events.id ASC`. Past puts rows that took place (confirmed, published) first, then cancelled and failed rows; each group by `events.starts_at DESC, events.id DESC`. Hidden-event rows sit at their event's date without exposing it | `id` breaks ties, as the event list does since `839012d`. Cancelled and failed rows go last, so a cancelled event months away does not sit above yesterday's session |
| D5 | "Happening now" | Computed in the client from `starts_at` and `ends_at`. `ends_at` is added to the event summary | Simple; uses the viewer's clock |
| D6 | Sorting | In SQL, joining `events` | One ordered query per section; no Ruby sort |
| D7 | Frontend | Headings Upcoming and Past. Empty states "No upcoming events" and "No past events". Cancel button only in Upcoming, and not on an event happening now. Labels in Past: "Cancelled" (participant), "Event cancelled" (organizer cancellation), "Registration failed" | PO and engineer |

## Design

### Backend

`Api::Me::RegistrationsController#index`:

```ruby
now = Time.current
base = current_user.registrations.joins(:event).includes(:event)

upcoming = base
  .where(status: "confirmed")
  .where("events.ends_at > :now AND events.status = 'published'", now: now)
  .order("events.starts_at ASC, events.id ASC")
  .load

# The negation of Upcoming, written out rather than as a NOT IN subquery. Change both together: test 11b fails if they drift.
past = base
  .where("registrations.status <> 'confirmed' OR events.ends_at <= :now OR events.status <> 'published'", now: now)
  .order(Arel.sql(<<~SQL.squish))
    CASE WHEN registrations.status = 'confirmed' AND events.status = 'published' THEN 0 ELSE 1 END,
    events.starts_at DESC, events.id DESC
  SQL
  .load
```

**Indexes.** No new indexes. Both queries start from `registrations.user_id`, served by the existing index (one person has at most a few hundred rows), join `events` by primary key, and sort that handful of rows in memory. `EXPLAIN ANALYZE` on development data, for a user with 49 registrations, ran each query in about 0.5 ms with a 26–28 kB in-memory sort. An index on `events.ends_at` or `events.status` would not help, because the queries never search events by date, and no index can serve an order on `events` while filtering on `registrations`. Separately, `index_registrations_on_user_id` duplicates the leading column of the unique `(user_id, event_id)` index; dropping it is a tech-debt change outside this ticket.

The two conditions together cover every registration exactly once: a row is Upcoming when all three Upcoming conditions hold, and Past when at least one fails. `events.ends_at` is `NOT NULL`, so no row falls outside both.

- One `visible_event_ids_for` lookup over both lists, as today, so a hidden event is still sent without its summary.
- Response: `{ "upcoming": [...], "past": [...] }`, each row `Registration#as_json_api` as today.
- `Registration#event_summary` adds `ends_at`.

**On "Happening now" and the two clocks.** The server decides the section with its clock (D3); the client decides "Happening now" with the viewer's clock (D5). If the two disagree by a few minutes, an event can sit in Upcoming without the label, or show it just after ending. That is acceptable for a label. Sections never disagree, because only the server decides them.

**On the organizer cancellation window (MF-102).** Until `CancelEventRegistrationsJob` reaches a registration, it is still `confirmed`, so it would sit in Upcoming for an event that is already cancelled. To keep the PO's rule ("a cancelled session is not in Upcoming"), Upcoming also requires `events.status = 'published'`. A registration for a cancelled event goes to Past immediately, labelled "Event cancelled".

### Frontend

- `core/models.ts`: `MyRegistrations { upcoming: Registration[]; past: Registration[] }`; `ends_at` on the registration's event summary.
- `core/forum-api.ts`: `registrations()` returns `MyRegistrations`.
- `pages/registrations.component.*`: two signals, `upcoming` and `past`; two sections with headings and empty states. A row in Upcoming shows "Happening now" when `starts_at <= now < ends_at`. The Cancel button appears only in Upcoming, and not while the event is happening now (`Registrations::Cancel` raises `EventStarted` once `starts_at <= now`). A row for a hidden event has no dates, so it keeps the button and the server decides. After a successful cancel, the list reloads, so the row moves from Upcoming to its place in Past.
- Past labels: "Cancelled" when `cancelled_by` is `participant`; "Event cancelled" when the event is cancelled or `cancelled_by` is `organizer`; "Registration failed" for `failed`.
